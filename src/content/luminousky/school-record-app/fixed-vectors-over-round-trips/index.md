## 전부 통과하는데 파일이 열리지 않는다

[필드 단위 암호화](../field-level-encryption-aes256gcm-pbkdf2/)에 대한 테스트는 상당한 규모였다. 키 파생, 필드 암호화, 잠금 해제, 비밀번호 변경, 전체 복호화까지 경로마다 검증이 존재했다. 그런데 그 테스트가 전부 라운드트립이었다. 같은 빌드로 암호화하고 같은 빌드로 복호화한다.

이 구조에서는 저장 형식이나 키 파생이 변경되어도 테스트가 실패하지 않는다. 암호화 함수와 복호화 함수가 함께 변경되므로 서로 일관된다. 깨지는 것은 이미 암호화를 적용해 둔 사용자의 파일뿐이고, 그 파일은 테스트 대상에 존재하지 않는다.

실제로 확인했다. PBKDF2 반복 횟수를 600,000에서 100,000으로 변경하면 기존 사용자 파일은 영영 열리지 않는다. 그 상태에서 암호화 테스트는 하나도 실패하지 않았다.

## 고정 벡터

현재 코드로 생성한 값을 소스에 기록했다. 파생 키, 검증 토큰, 암호화된 이름과 내용, 공백과 여러 줄 입력의 결과가 대상이다. 앞으로 어떤 라이브러리를 올리든 이 값이 그대로 복호화되어야 한다.

여기에 더해, 고정 벡터를 삽입한 DB를 생성하고 잠금 해제부터 조회까지 평소 경로로 읽히는지 확인하는 테스트를 추가했다. 함수 단위 검증은 함수가 살아 있다는 것만 증명하지만, 이 테스트는 배포된 사용자 파일이 열린다는 사실을 직접 증명한다.

민감도도 측정했다. 반복 횟수 변경, nonce 길이 변경, 저장 구분자 변경을 각각 적용해 실제로 실패가 발생하는지 확인했다. 실패하지 않는 고정 벡터는 존재하지 않는 것과 같다.

이 테스트가 실패할 때 값을 다시 생성하는 행위는 금지다. [스키마 지문](../schema-fingerprint-lock/)과 성격이 동일하며, 실패는 저장 형식이 변경되었다는 신호다.

## 6개가 한꺼번에 깨진 의존성 PR

배경에는 3주간 정체된 dependabot PR이 있었다. cargo 의존성을 backend 그룹 하나로 통합해 둔 탓에, 서로 무관한 이유로 여섯 개가 동시에 실패했다. 하나를 해결하면 다른 하나가 드러나는 상태가 반복되었고, 그동안 보안 업데이트도 함께 정체되었다.

그룹을 나누는 기준을 고민하면서 두 가지 후보가 있었다. 하나는 업데이트 빈도, 다른 하나는 검증 방법이다. 빈도 기준은 PR 수를 고르게 분산하지만, 깨졌을 때 무엇을 확인해야 하는지는 여전히 섞여 있다.

검증 방법을 기준으로 분할했다. 확인 절차가 다르면 다른 그룹이다.

- crypto: 고정 벡터로 저장 형식과 키 파생의 불변을 확인한다. RustCrypto 계열은 digest와 aead 세대를 공유하므로 개별 승격이 불가능해 하나로 유지한다.
- database: 번들 SQLite 엔진이 함께 올라가므로 실제 파일로 확인한다.
- tauri: 실패하면 앱이 기동하지 않는다. 위험 등급이 다르다.
- backend: 나머지.

npm과 GitHub Actions 쪽도 같은 기준으로 재편했다.

## 실제 파일 검증 하니스

database 그룹의 검증 방법을 "실제 파일로 확인한다"라고 정의하려면 그 수단이 필요했다. rusqlite 0.31에서 0.40으로 올리면서 번들 SQLite가 3.45에서 3.53으로 상승했고, 그 순간 기존 테스트의 공백이 명확해졌다. 모든 테스트가 in-memory DB를 `schema.sql`로 새로 생성하므로, 예전 엔진이 기록한 실제 파일을 여는 경로는 한 번도 실행되지 않는다.

하니스는 파일 열기부터 무결성 검사, 외래키 검사, 스키마 지문 대조, 마이그레이션, 조회, 쓰기와 되읽기, 삭제, 재열기까지 실제 커맨드 경로로 확인한다. 항상 사본에서 작업하고 원본이 바이트 단위로 변경되지 않았는지 검사한다. 학생 개인정보가 포함되어 있으므로 내용은 출력하지 않고 개수만 출력한다.

실제 파일이 필요하므로 CI에서는 실행되지 않는다. `#[ignore]`로 표시하고 환경 변수로 경로를 지정해 수동 실행한다. 자동화하지 못하는 검증이지만, 자동화할 수 있는 형태로 축소하면 검증하려던 대상이 사라진다.
