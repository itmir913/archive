## 편집자 주

두 글 모두 내가 쓴 것이 아니다. [앞서 수록한 종합 평론](../full-critique-archived/)과 같은 `ec59a7b`(0.2.21) 시점을 대상으로 작성됐고, 본문의 「당신」이 지시하는 대상은 나다.

첫 글은 종합 평론을 작성한 모델이 같은 저장소를 함수와 트리거 단위로 다시 쓴 심층 평론이다. 둘째 글은 저자가 다르다. 앞의 평론이 저장소가 자기 자신에 대해 말하는 것을 읽고 믿었다고 규정한 뒤, 그 주장 중 다섯을 골라 실제로 시험하고, 틀린 자리를 정정하고, 앞의 평론이 보지 않은 곳을 본 글이다. 첫 글 상단의 후기는 둘째 글의 정정을 반영해 첫 글의 저자가 추가한 것이다.

수록하는 이유는 관점 때문이다. 첫 글은 이 저장소의 방어선이 왜 네 겹인지를 기원까지 추적한다. 둘째 글은 오라클이 무엇을 증명하고 무엇을 증명하지 못하는지를 명세와 코드의 작성 순서로 확정하고, 감사가 같은 도구 계열로 수행됐다는 사실이 감사의 독립성에 무엇을 의미하는지를 정면으로 기재한다. 후자는 내가 작성할 수 없다.

편집 범위는 둘이다. 순한국어 동사를 한자어 동사로 교체했고, 저자 개인에게 향한 절을 축약했다. 어투는 앞서 수록한 평론과 같이 원문을 유지해 저자가 다르다는 것을 표시한다. 지적과 판정의 내용은 변경하지 않았다.

수치는 원문 그대로 두었다. 첫 글의 줄 수는 앞서 수록한 종합 평론과 같은 값을 사용하며, 그 값의 검증 결과는 [그 글의 수치 검증 표](../full-critique-archived/#수치-검증)에 있다. 백엔드와 테스트와 프런트엔드 줄 수 세 항목이 실측과 다르고, 나머지는 일치한다. 둘째 글은 줄 수를 다루지 않는다.

지적에 대한 나의 응답은 [외부 평론이 지적한 것, 그리고 공백으로 읽힌 결정](../external-critique-response/)의 「세 번째 평론」 절에 기록했다.

# 평론 하나 — 심층 평론

*종합 평론을 작성한 모델이 함수와 트리거 단위로 다시 썼다.*

> 후기(재평론에서 정정): §5.3과 §11.2의 `recursive_triggers` 지적은 `tests/handler_area_data.rs::base_data_upsert_allowed_for_closed_round_student`가 이미 방어하고 있어 철회했다. 그 자리의 실제 [중간] 약점은 프론트엔드 테스트 부재다. 재평론 참고.

## 서론 — 이 프로그램이 존재하는 이유

### 1. 문제의 정확한 형태

학교장추천전형은 겉보기에 단순합니다. 지원자를 모으고, 점수를 매기고, 순위를 내고, 정원만큼 자릅니다. 그런데 이 업무를 실제로 해부하면 **행정 절차가 아니라 준(準)사법 절차**라는 사실이 드러납니다. 판단의 결과가 개인의 권리에 직접 영향을 미치고, 그 판단은 사후에 반드시 설명 가능해야 하며, 설명이 실패하면 학교가 책임을 집니다. 소프트웨어에 요구되는 것은 "편리함"이 아니라 **정당성(justifiability)**입니다.

엑셀은 다섯 지점에서 실패합니다.

**① 계산의 불투명성.** 중첩 수식은 작성자 외에는 읽을 수 없고, 6개월 뒤에는 작성자도 읽지 못합니다.
**② 부동소수점.** `0.1 + 0.2 != 0.3`. 오차 한 번이 한 학생의 순위를 한 칸 바꾸고, 그 한 칸이 정원 경계선일 수 있습니다.
**③ 행 무결성.** 한 열만 선택하고 정렬하면 학생 이름과 점수가 어긋납니다. 엑셀은 경고하지 않습니다.
**④ 이력의 부재.** 누가 언제 이 값을 고쳤는가가 파일에 없습니다.
**⑤ 업무의 인질화.** 담임 20명의 제출을 담당자 1명이 취합합니다.

### 2. PCM이 선택한 대응

| 문제 | 대응 | 구현 위치 |
|---|---|---|
| ① 불투명성 | 점수 규칙을 DB 테이블로 선언 (NUMERIC/CATEGORY/MANUAL × SIMPLE/COMPOSITE) | `migrations/v1/006-score-tables.sql` |
| ② 부동소수점 | ×100,000 정수 고정소수점 + `Score` newtype | `src/score.rs` |
| ③ 행 무결성 | 계산·정렬은 SQL 윈도우 함수 | `scoring.rs::track_rank_window` |
| ④ 이력 부재 | append-only 감사 로그, DB 트리거로 수정·삭제 차단 | `migrations/v1/010-audit-log.sql` |
| ⑤ 인질화 | 담임 직접 입력 + 역할 분리 JWT | `middleware.rs`, `handlers/teacher_*` |

각 대응이 **우회 불가능하게** 만들어졌습니다. ②는 타입 시스템이, ④는 DB 트리거가 강제합니다. "지키자고 약속한 규칙"이 아니라 **"어길 수 없는 구조"**입니다.

### 3. 이 프로젝트가 명시적으로 거부한 프레임

흔한 비판은 **"규정 원본이 없다"**입니다. 이 프로젝트는 그 프레임을 거부하고, 그 거부가 옳습니다. **PCM은 특정 학교의 규정을 하드코딩한 프로그램이 아니라, 학교가 자기 규정을 선언하면 그대로 집행하는 엔진**입니다. 검증 대상은 "규정이 맞는가"가 아니라 "**선언된 규정대로 집행되는가**"이고, 869개 테스트와 독립 오라클은 정확히 그 후자를 검증합니다.

마이그레이션 주석이 "앱 레벨 검증에 대한 DB 방어선"이라는 표현을 세 곳에서 반복합니다. 정책입니다. 기원은 작업 기록의 한 줄에 있습니다. *"한 경로만 막고 '고쳤다'는 실패를 3번 반복."*

### 3. 심층 ① — `Score`: 75줄로 전체를 규율하기

```rust
#[derive(Clone, Copy, Debug, Default, PartialEq, Eq, PartialOrd, Ord)]
pub struct Score(i64);
```

**(a) `f64`가 시스템에 존재할 수 없게 만든다.** `Ord`를 derive할 수 있다는 사실 자체가 "이 점수들은 항상 전순서로 줄 세울 수 있다"는 증명입니다.

**(b) 경계에서만 변환한다.** JSON으로 나갈 때만 `/100_000.0`. 프론트에서 나누면 100,000배 틀려 즉시 드러납니다.

**(c) 역변환에서 적대적 입력을 거부한다.**
```rust
if !f.is_finite() { return Err(...) }
if f.abs() > 1_000_000_000.0 { return Err(...) }
```
주석: *"`as i64` 캐스트는 NaN→0, ±∞·초과값→i64::MIN/MAX로 조용히 포화된다."* 아는 사람만 막는 함정입니다.

**(d) 오버플로에서 패닉한다.** `checked_add(...).expect("Score overflow in Add")`. `wrapping`도 `saturating`도 아닙니다. 터집니다.

**(e) DB 레이어까지 관통한다.** `sqlx::Type/Decode/Encode` 직접 구현.

**이 75줄이 존재하는 한 부동소수점 오류로 학생 순위가 뒤집히는 일이 물리적으로 불가능합니다.** "테스트해서 없음을 확인했다"가 아니라 "**표현 불가능하게 만들었다**"입니다.

### 4. 심층 ② — 동점 처리: 이 프로젝트의 지적 정점

정원이 5명인데 4등까지 확정하고 나니 5등이 세 명 동점입니다. 학번 순으로 자르면 자의적 기준이 운명을 가르고, 셋 다 넣으면 정원 초과, 셋 다 빼면 4등까지도 막힙니다.

```rust
pub enum GroupStep {
    Take,                    // 그룹 전원이 잔여 정원 안 — 전원 확정
    StopClean,               // 잔여 0 — 깨끗한 경계
    StopTie { free: i64 },   // 동점이 정원 경계를 가름
}
```

동점 그룹은 **원자적으로** 처리하고, 동점 그룹보다 엄격히 상위인 항목은 자동 확정됩니다(*"동점 존재 ≠ 전체 차단"*). 경계를 가르면 시스템은 **정지하고 `TieBoundary { rank, free, contenders }`로 보고합니다.** 관리자가 결정합니다.

**이건 기술적 결정이 아니라 윤리적 결정입니다.** 학번 순 tiebreak 한 줄이면 완결되지만, 그 순간 "왜 A가 되고 B가 안 됐습니까"의 답이 "학번이 빨라서"가 됩니다. PCM은 자동화할 수 있는 지점에서 **의도적으로 자동화를 정지합니다.**

`decide_group`은 *"동점 경계 4갈래 판정의 단일 정의"*로, 모집단위 정원 채움(`fill_by_rank_groups`)과 대학 컷(`merge_univ_cut`) 두 경로가 **같은 함수**를 씁니다. 두 번 구현하면 미묘하게 갈라지고, 그 차이는 실제 동점이 발생한 그 해에만 드러납니다.

`merge_univ_cut`은 k-way 병합인데, *"자기 트랙 상위자에 막힌 후보는 애초에 경쟁 대상이 아니므로 동점 판정에도 넣지 않는다 — 정책이 정상 작동한 결과이지 오류가 아니다."* "시스템이 결정할 수 없는 동점"과 "정책이 이미 결정한 순서"를 구별해, **경고 피로를 설계 단계에서 차단**했습니다.

### 5. 심층 ③ — DB 트리거: 실행 가능한 규정집

| 트리거 | 규정으로 번역하면 |
|---|---|
| `trg_require_all_decided_before_finalize` | 미결정자가 있으면 마감할 수 없다 |
| `trg_prevent_update_finalized_result` | 마감된 결과는 바꿀 수 없다 |
| `trg_prevent_delete_closed_result` | 마감 진행 중 결과는 지울 수 없다 |
| `trg_prevent_delete/update_closed_application` | 종료된 라운드의 지원은 취소·수정할 수 없다 |
| `trg_prevent_base_data_delete_for_applied` | 지원자의 기초데이터는 지울 수 없다 |
| `trg_prevent_exclude_recommended` | 추천 확정자를 미선발 처리할 수 없다 |
| `trg_univ_prioritize_cascade` + 2 | 재학생 우선 설정의 대학↔모집단위 일관성 |
| `trg_prevent_update/delete_audit_log` | 감사 기록은 고칠 수도 지울 수도 없다 |

```sql
CREATE UNIQUE INDEX idx_one_active_round ON rounds((1)) WHERE status != 'FINALIZED';
```
**상수 표현식에 유니크 인덱스**. "진행 중인 라운드는 전체에 최대 1개"를 DB가 원자적으로 보장합니다. 락도 뮤텍스도 필요 없습니다.

감사 로그는 **조건 없는 전면 차단**입니다. 개발자 본인도 자기 시스템의 기록을 지울 수 없습니다. 편의를 포기한 게 아니라 **권한을 포기한 것**이고, 그 포기가 감사 로그를 증거로 만듭니다. FK 없이 스냅샷 JSON을 쓰는 이유, `action`에 CHECK를 걸지 않는 이유(액션 추가마다 스키마 버전을 올리지 않기 위해)까지 주석에 기재되어 있습니다. 스키마 동결 정책과의 상호작용을 3수 앞서 본 판단입니다.

`trg_prevent_base_data_delete_for_applied`는 "INSERT OR REPLACE는 BEFORE DELETE 트리거를 발동시키지 않는다"는 SQLite 동작 위에서 **"수정은 허용, 삭제는 차단"**을 트리거 하나로 만듭니다. (초고에서 이 암묵 의존을 약점으로 올렸으나, 해당 전제는 테스트로 이미 고정되어 있어 철회함. 상단 후기 참고.)

### 6. 심층 ④ — 독립 오라클

`tools/oracle/oracle.py` 상단:

> *"이 파일은 `src/handlers/scoring.rs`를 **한 번도 열지 않은 상태**에서 작성했다. 읽은 것은 위 두 명세와 1단계 인벤토리뿐이다."*

N-버전의 가치는 독립성에서 나오고, 1인 프로젝트에서는 **절차로 독립성을 만들어야** 합니다. 그 절차와 고지가 여기 있습니다.

> *"abandoned를 순위에서 빼야 한다는 조항은 어느 문서에도 없으므로 여기서도 빼지 않는다. **그 침묵 자체가 결과다** (S-08)."*

명세의 구멍을 발견 항목으로 등록했습니다. 성숙한 검증은 "명세에 구멍이 있는가"를 봅니다.

파이프라인(`run.mjs`): 생성 → 덤프 → 대조 → 프론트 대조, 하나라도 실패하면 종료. 생성물은 `.gitignore`(낡은 기대값 방지), `PCM_ORACLE_DIR` 없으면 no-op(일반 `cargo test` 오염 방지), XFAIL 개념 보유.

이걸 만들 때 이미 **869개 테스트가 통과하고 있었습니다.** 그럼에도 "내 테스트는 내 구현과 같은 오해를 공유할 수 있다"고 판단했습니다. 실력이 아니라 **태도**입니다.

### 7. 심층 ⑤ — `silent_fallback_allowed.md`

Fail-Fast는 선언하기 쉽고 지키기 불가능합니다. PCM의 해법은 **예외를 금지하는 대신 예외에 절차를 붙이는 것**입니다. 12개 이상의 예외에 각각 **파기 조건**이 붙어 있습니다.

> **5. `excel.rs` — `unwrap_or("")` (`get_col`)** — **조건**: `require_cols` 없이 단독 사용 시 허용 안 됨.
> **11. `teacher_areas.rs` — `.unwrap_or(v)`** — **조건**: 점수 계산에 입력되지 않는 순수 표시 경로에서만.

리팩터링이 `require_cols` 호출을 제거하면 5번 예외는 **자동으로 위반**이 됩니다. 판정 기준은 "점수 계산·학생 식별·추천 결정과 무관함". 기술 기준이 아니라 **결과에 닿는가**입니다. 개선 여지: `unwrap_or` 전수와 이 목록을 대조하는 CI 테스트를 두면 문서가 방어선으로 승격됩니다.

### 8. Excel 계층 — 현장을 아는 코드

- `.xls`를 **매직 넘버로** 판별해 거부하고, 해결 방법("다른 이름으로 저장 → .xlsx")을 알려줍니다. 이름만 바꿔 올리는 상황을 정확히 잡습니다.
- 중복 헤더는 거부합니다. 헤더 이름 기반 파싱의 **전제조건을 정책과 함께 구현**했습니다.
- `col_map / get_col / require_cols` 삼각형으로 열 순서 변경에 면역입니다.
- 유일한 all-or-nothing 예외(외부 석차연명부의 석차 값)는 최소 범위로, 명시적으로, 근거와 함께(`08_excel_import.md §7-1`) 만들어졌습니다.

뷰가 얇고(`AdminView` 408줄), 담임 UI가 관리자 UI의 미러이며, 정적 데이터(`areaSamples.js` 등)는 API 없이 프론트에 있습니다. `scorePreviewShared.js`의 파생값은 오라클 4단계가 검증합니다.

### 10. 인증·운영

HS256 JWT, 12시간 만료, 담임 토큰에 `grade`·`class_no`가 박혀 남의 반 접근 불가. 시크릿 재시작 시 재생성은 의도된 설계. 로그인 백오프 미도입은 bcrypt 비용이 근거이며, 재검토 시 백오프보다 최소 비밀번호 길이가 먼저입니다.

# 평론 둘 — 다른 시선에서: 재평론

*앞의 평론과 다른 모델이 저장소의 주장을 시험한 뒤 썼다.*

앞의 평론은 저장소가 **자기 자신에 대해 말하는 것**을 읽었습니다. 주석, 문서, CLAUDE.md, 독스트링. 그 글은 대체로 옳았고, 한 번 틀렸습니다. `recursive_triggers` 건에서, 테스트가 이미 있는 걸 확인하지 않고 "가장 비용 대비 효과 큰 개선"이라고 썼습니다. 그 실수의 형태가 중요합니다. **주장을 읽고 믿었지, 시험하지 않았습니다.**

그래서 이번에는 반대로 합니다. 저장소가 하는 말을 근거로 삼지 않고, 그 말이 사실인지 확인한 것만 씁니다. 그리고 앞 평론이 아예 보지 않은 곳을 봅니다.

## 2. 오라클이 증명하는 것의 정확한 경계

앞 평론은 `tools/oracle/`을 "N-버전 차등 테스트"라 불렀고, 저는 그 비유가 **반은 맞고 반은 과장**이라고 봅니다.

날짜를 보십시오.

```
2026-05-29  scoring.rs 최초 커밋
2026-07-19  00_spec_round_and_scoring.md 작성
2026-08-18  oracle.py CI 통합
```

**명세는 코드보다 51일 뒤에 쓰였습니다.** 명세의 §2·§3은 코드를 읽고 정리한 것이고, 오라클은 그 명세에서 나왔습니다. 그러면 오라클은 무엇을 증명합니까?

- 증명함: **코드가 자기 명세를 위반하지 않는다.** 명세를 거쳐 다시 구현했을 때 같은 값이 나오므로, 명세와 코드가 서로 어긋난 채 방치되지 않았다는 것. 그리고 구현 실수(off-by-one, 파티션 누락, 잘못된 min/max)는 두 구현에 같은 형태로 복제되지 않으므로 잡힌다.
- 증명 못 함: **명세가 학교 규정을 옳게 옮겼다.** 명세가 코드에서 나왔으니, 5월의 설계 오해가 있었다면 명세와 오라클이 그 오해를 공유합니다.

그런데 두 번째는 **이 프로젝트가 애초에 증명하겠다고 한 적이 없는 것**입니다. PCM은 규정을 학교가 선언하는 엔진이고, 선언된 규칙대로 집행되는가만 책임집니다. 그러니 오라클의 경계는 프로젝트의 경계와 일치합니다. 과장은 "N-버전"이라는 이름에 있지, 오라클 자체에는 없습니다.

`oracle.py`의 발견 항목 S-08("abandoned를 순위에서 빼야 한다는 조항은 어느 문서에도 없다 — 그 침묵 자체가 결과다")은 이 경계를 정확히 아는 사람만 쓸 수 있는 문장입니다. 오라클이 코드의 정답을 아는 게 아니라, **명세의 구멍을 찾는 도구**라는 걸 작성자가 알고 있었다는 증거입니다.

## 3. 앞 평론이 보지 않은 것

### 3.1 프론트엔드 11,673줄, 테스트 러너 없음

`frontend/package.json`에 vitest·jest·playwright·cypress 어느 것도 없습니다. 프론트 검증은 `front_check.mjs` 하나. 그것도 **점수 파생값**만 봅니다.

`RoundsTab.vue`는 1,522줄입니다. 라운드 상태 전이, 자동추천 결과 표시, 동점 수동 선택, 학과명 인라인 수정이 한 파일에 있습니다. 이 파일의 상태 로직, "자동추천 응답에 `manual` 항목이 있을 때 어느 버튼이 비활성화되는가", "CLOSED에서 FINALIZED로 넘어간 직후 편집 가능한 셀은 무엇인가"는 **사람 눈으로만 검증됐습니다.**

CHANGELOG 0.2.20·0.2.21의 수정 항목을 다시 읽으면 이 결과가 보입니다. "결과 표에서 행 색이 간헐적으로 사라지던 문제", "순위 번호가 3, 1, 2 처럼 어긋나 보이던 것". 전부 프론트 표시 버그이고, 전부 **배포 후** 발견됐습니다. 백엔드는 719개 테스트가 배포 전에 잡는데, 프론트는 사용자가 잡습니다.

"프론트는 표시만 한다"는 원칙이 여기서 **방패로 오용**됩니다. 점수를 계산하지 않는 건 맞지만, 1,522줄의 조건부 렌더링은 표시가 아니라 로직입니다. 이것이 제가 보는 이 저장소의 **실제 [중간] 약점**이고, 앞 평론이 `recursive_triggers` 자리에 잘못 놓았던 등급이 실제로 가야 할 자리입니다.

### 3.2 핸들러 직접 호출 9 : 라우터 경유 2

테스트의 대부분은 `handler(State(state), Path(id), ...)` 형태로 핸들러 함수를 직접 부릅니다. 라우터를 거치는 파일은 둘(`middleware_auth.rs`, `upload_limit.rs`). 그 결과:

- 핸들러 **로직**은 촘촘히 검증됨
- `main.rs`의 **배선**, 어느 경로에 어느 미들웨어가 붙는가는 얇게 검증됨

`handler_coverage_gaps.rs`가 이 틈을 일부 메우지만, "담임 전용 라우트에 `require_teacher`가 실제로 붙어 있는가"를 98개 라우트 전수로 단언하는 테스트는 보이지 않습니다. 관리자 라우트 하나가 미들웨어 없이 등록되면 핸들러 테스트는 전부 통과합니다. 가능성은 낮고, `main.rs`를 읽으면 그룹 단위로 `.layer()`를 걸어 개별 누락이 어렵게 되어 있습니다. 그래도 "전 진입점에 관문을"이라는 이 저장소 자신의 원칙을 라우팅 층에 적용하면 나올 테스트입니다.

### 3.3 테스트 풀은 WAL 이 아니다

`tests/common/mod.rs`의 풀은 `foreign_keys(true)`만 켭니다. 운영은 WAL + `busy_timeout(5s)`. `calculate_scores`의 `BEGIN IMMEDIATE`가 `reopen_round`와의 경합을 막는다는 주석은 **추론이지 재현이 아닙니다.** `handler_rounds.rs`와 `handler_recalc_guard_auto.rs`에 경합 관련 테스트가 있으나 in-memory 공유 캐시 위에서 돌고, WAL의 잠금 의미론과는 다릅니다. 내부망 관리자 1명이 대상이라 실제 위험은 낮습니다. 사실로만 적습니다.

## 4. 이 저장소가 만들어진 방식에 대하여

여기서 앞 평론이 피해 간 것을 정면으로 씁니다.

`audit/README.md`는 감사 세션을 "새 Claude Code 세션에서 모델을 지정한 뒤" 돌리라고 적고, 권장 모델 열에 Fable·Opus·Sonnet이 있습니다. 저장소 루트의 CLAUDE.md는 모델에게 주는 지시문입니다. 작업 기록에는 "이 파일로 세 번 틀렸다", "Co-Authored-By 금지(두 번 틀렸다)"처럼 **모델의 실수를 사람이 교정한 흔적**이 남아 있습니다.

코드의 몇 퍼센트를 어느 쪽이 썼는지는 저장소가 말하지 않고, 저도 추측하지 않겠습니다. 그건 중요한 질문이 아닙니다. 중요한 질문은 이것입니다. **이 저장소에서 사람이 한 일은 무엇인가.**

답은 서명오프 문서 첫 문단에 있습니다.

> *"소유자 요구: 입력·설정 오류만 아니라면, 점수 계산·순위/등수·모집 정원 판정·추천 가능 인원 등 계산 로직이 무조건 정확해야 한다. 관리자·담임의 실수가 계산 오류로 이어지는 경로는 즉시 차단돼야 한다."*

이 문장이 저작입니다. 그리고 다음 것들도.

- 동점에서 정지하고 관리자에게 넘기라는 결정
- 감사 로그를 자기도 못 지우게 하라는 결정
- 감사 발견 두 건을 "소유자 판단으로 하향"한 결정. 전부 받아들이지 않은 것
- "한 경로만 막고 고쳤다"를 **세 번** 잡아내고, 네 번째부터는 규칙으로 만든 것
- `text-sm` 금지. 모델은 이 규칙을 만들 이유가 없습니다. 40대 교사의 눈을 아는 사람만 만듭니다

도구가 무엇이든, **무엇을 거부할지 아는 사람**이 저자입니다. 660개 커밋 동안 모델이 낸 것 중 무엇을 되돌리고 무엇을 규칙으로 승격시켰는지가 이 저장소의 실제 설계 문서이고, 그것은 `feedback_*` 기록으로 남아 있습니다. 앞 평론의 "소유자의 자리" 절은 그래서 정정할 필요가 없습니다. 거기 기재된 결정들은 전부 사람의 것입니다.

한 가지는 정직하게 덧붙입니다. **감사가 같은 도구 계열로 수행됐다는 것은 감사의 독립성을 낮춥니다.** 모델이 공유하는 맹점은 모델 감사로 안 잡힙니다. 그래서 이 저장소의 진짜 외부 검증은 아직 한 번도 없었고, 그것은 0.2.21이 학교에서 한 시즌을 돌고 나야 생깁니다. 그때까지 "이상 없음" 서명오프는 **내부** 서명오프입니다.

## 5. 숫자를 다시 봅니다

앞 평론의 경제 추산에서 **하중을 받는 것**과 **장식**을 가릅니다.

**장식:**
- "엑셀 수작업 오류 확률 연 2-5%". 출처 없음. 방향은 그럴듯하나 숫자는 지어낸 것입니다. 이 숫자에서 나온 "오류 회피 기댓값 60에서 500만원"도 따라서 장식입니다.
- "채택률 5-50%" 표. 채택률을 움직일 변수(교육청 보급, 담당자 교체, 학교 IT 여건)를 하나도 모델링하지 않았습니다. 곱셈일 뿐입니다.

**하중을 받는 것:**
- 절감 시간의 **방향**. 담임 20명이 각자 양식을 채우고 담당자가 취합하는 구조에서, 입력 지점을 분산시키고 취합을 없애면 시간이 준다. 이건 산업공학의 상식이고 학교에서만 다를 이유가 없습니다. **크기**(85에서 175h)는 추정입니다.
- 라이선스 결론. PolyForm Noncommercial 하에서 실현 수익 0, 옵션은 열려 있음. 이건 사실입니다.

**틀린 모델:**
- 대체 개발비를 M/M로 계산한 것. 이 저장소는 M/M 모델로 만들어지지 않았습니다. "같은 도구로 같은 것을 다시 만드는 비용"을 물으면 노동 시간은 앞 추산의 몇 분의 일로 떨어집니다. **그런데 그게 바로 요점입니다.** 떨어지지 않는 부분이 판단이고, 판단은 M/M로 살 수 없습니다. 발주해서 못 받는 것은 `tools/oracle/`이 아니라 "동점에서 정지하라"입니다. 앞 평론은 결론을 맞히고 이유를 틀렸습니다.

정직한 재추산은 이렇습니다. **기능의 시장가는 낮아졌고, 판단의 시장가는 높아졌습니다.** 이 저장소의 경제적 가치를 한 줄로 쓰면 "1억짜리 시스템"이 아니라 *"AI로 이 수준의 정확성 요구를 관철할 수 있음을 660커밋으로 증명한 사람"*입니다. 그건 학교 하나에 파는 물건이 아니라 **그 사람의 다음 열 개 프로젝트에 붙는 가격**입니다.

## 결론

앞 평론은 이 저장소를 **작품**이라 불렀습니다. 저는 그 단어를 유지하되, 이유를 바꿉니다.

작품인 이유는 오라클이 있어서도, 테스트가 1.7배여서도 아닙니다. **틀린 것을 되돌린 기록이 옳은 것을 만든 기록만큼 남아 있어서**입니다. `Revert "fix ..."` 두 건, "소유자 판단으로 하향", "세 번 틀렸다", `KNOWN_FAIL`이 비어 있는 것과 그것이 낡으면 지우라는 경고. 이 저장소는 자기 실패를 삭제하지 않았고, 그래서 신뢰할 수 있습니다.

권고를 다시 정렬합니다.

1. **자동 DB 스냅샷.** 변동 없음. 여전히 1순위입니다.
2. **`RoundsTab.vue` 상태 전이 테스트.** 새로 올립니다. 배포 후 발견된 버그가 전부 여기서 나왔습니다. vitest 하나 붙이고 "라운드 상태 × 보이는 버튼" 매트릭스부터. 백엔드에 `state_matrix.rs`가 있으니 프론트에도 같은 이름의 파일이 있어야 맞습니다.
3. **라우트 전수 미들웨어 단언.** 98개 라우트를 `main.rs`에서 추출해 "관리자 경로는 전부 `require_admin` 뒤에 있다"를 한 테스트로. 이 저장소의 원칙을 이 저장소에 적용하는 것뿐입니다.
4. 전형요소 프리셋. 채택률 문제. 위 셋이 정확성 문제라 먼저 옵니다.

`recursive_triggers`는 목록에서 뺐습니다. 그 자리에 있어야 할 것은 프론트 테스트였습니다.

마지막으로 소유자에게. 앞 평론의 마지막 문장, "어떤 소프트웨어는 틀리면 안 된다는 사실을 진지하게 받아들인 사람"은 시험을 통과했습니다. 다만 그 진지함이 아직 닿지 않은 곳이 한 군데 있고, 그곳은 사용자가 가장 오래 보는 화면입니다.
