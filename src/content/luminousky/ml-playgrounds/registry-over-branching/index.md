## 세 축이 대부분을 결정한다

이 도구의 화면과 기능은 세 축의 조합 위에 있다.

| 축 | 결정 시점 | 값 |
|---|---|---|
| 데이터 종류 | 프로젝트를 생성할 때 확정 | 표 / 이미지 |
| 과제 유형 | 학생이 선택 | 분류 / 회귀 / 군집 |
| 실행 위치 | 항목이 선언 | 순수 JS / scikit-learn / 서버 |

KNN은 분류와 회귀 모두에서 사용할 수 있다. 로지스틱 회귀는 표에서만 사용할 수 있다.
혼동 행렬은 분류에만 존재한다. 결측치 처리는 이미지에 존재하지 않는다. 이들은 모두
동일한 형태의 사실인데, 초기에는 서로 다른 위치에 기술되어 있었다.

## 문제가 드러나는 시점

`v-if="taskType === 'classification'"`을 결과 화면에 기술하면 당장은 정상 동작한다.
문제는 군집이 추가되는 시점에 발생한다. 그때 수정해야 할 파일이 등록부 하나가 아니라
그 사실을 참조하는 화면 전부가 된다. 그리고 그중 하나를 누락했다는 사실을 컴파일러도
검사도 검출하지 못하고, 학생이 화면에서 발견하게 된다.

그래서 규칙을 하나 수립했다.

> "X는 Y에서만 사용할 수 있다"는 X의 등록부 항목에 기술한다. Y의 화면에 기술하지 않는다.

혼동 행렬이 분류 전용이라는 사실은 결과 화면이 아니라 혼동 행렬 항목에 있어야 한다.
결측치 처리가 표 전용이라는 사실은 전처리 화면이 아니라 해당 단계 항목에 있어야 한다.
알고리즘 선택에 `if/elif` 분기를 두지 않고 등록부에 등록한다.

## 회귀를 V1로 앞당긴 이유는 기능이 아니라 구조였다

초기 계획은 V1에 분류만 포함하고 회귀는 V2로 두는 것이었다. 이를 앞당겼는데, 근거는
구조였다.

과제 유형이 처음부터 복수여야 축이 축으로 기능한다. 분류 하나만 두면 `taskType`은
명목상 축이고 실질적으로는 상수다. 그 위에 구성한 등록부, 화면, 지표는 전부 단일 값을
전제로 맞춰지고, 회귀를 추가하는 시점에 구조를 변경해야 한다. 군집을 추가할 때 동일한
작업이 반복된다.

실제로 이 축 하나가 여러 지점을 구분했다. 지표 등록부, 타깃 자료형 판정, 결과 화면의
지표 열, 알고리즘 등록부의 지원 유형이 그것이다. 두 값으로 검증했기 때문에 세 번째
값인 군집을 추가하는 작업이 등록부에 한 줄을 추가하는 수준으로 축소되었다.

이미지도 동일했다. 이미지 코드를 작성하기 전에, 데이터 종류의 경계를 구분하는 순수한
리팩터링을 먼저 하나의 단계로 배치했다. 그 단계를 완료한 뒤에 이미지를 추가했다.

## 배열은 강제 장치가 되지 못한다

이 지점에서 실제로 문제가 발생했다. 등록부를 다음과 같이 기술했었다.

```ts
taskTypes: readonly TaskType[]
```

`['classification', 'regression']`으로 기술되어 있고 이후에 `clustering`이 축에
추가되면, 컴파일러는 아무런 오류를 보고하지 않는다. 부분집합은 언제나 유효한 배열이기
때문이다.

더 문제가 되는 경우도 있었다. `taskTypes: TASK_TYPES`로 기술한 항목은 새 유형을
지원한다고 자동으로 선언하게 된다. 해당 항목을 다시 검토하는 사람이 없는데 화면에는
표시된다.

그래서 축을 배열이 아니라 모든 값을 포함하는 `Record`로 변경했다.

```ts
// 결측치 처리 — 표에서만 사용, 과제 유형과는 무관
{
  id: 'missing-values',
  dataTypes: { tabular: true, image: false },
  taskTypes: { classification: true, regression: true, clustering: true },
  panel: …,
}
```

기술량이 늘어난다. 그 대가로 얻는 것이 목적이다. 데이터 종류에 값을 하나 추가하는 순간
모든 항목이 컴파일 오류를 발생시키고, 추가하는 사람이 항목마다 `true`/`false`를 판단해야
한다. 배열이었다면 아무 조치도 하지 않았을 것이고, 새 종류에서 결측치 처리가 표시되는지
여부는 우연에 맡겨졌을 것이다.

비어 있는 칸은 누락이 아니라 선언이다. "군집에는 제외되는 항목이 없다"고 명시적으로
기재한 것이다.

`Record`만으로는 부족하다는 것도 컴파일러를 실행해 확인했다.

```ts
export const X: readonly Capability[] = [ … ]   // 축이 증가하면 오류가 발생한다
export const X = [ … ] as const                 // 오류가 발생하지 않는다
```

타입 주석이 없으면 TypeScript는 리터럴을 그대로 추론하고 축이 증가해도 오류를 보고하지
않는다. 타입 주석이 강제 장치의 나머지 절반이었다.

## 잠금은 gate 함수 하나에서 산출한다

동일한 문제가 버튼에도 있다. `[학습하기]`가 활성화되려면 데이터가 있어야 하고, 타깃과
특성이 지정되어야 하고, 과제 유형을 선택해야 하고, 알고리즘을 하나 이상 선택해야 하고,
그 알고리즘이 현재 실행 위치에서 동작해야 한다. 조건은 앞으로 감소하지 않는다.

`:disabled="!hasData || !hasTarget || !hasFeatures || …"`를 템플릿에서 조립하면 세 가지
문제가 동시에 발생한다.

1. 조건을 하나 추가할 때 버튼까지 전달되는 컴포넌트의 시그니처가 전부 변경된다. 누락
   가능성이 제거되는 것이 아니라 위치만 이동한다.
2. 조건 하나를 확인하려고 화면 전체를 마운트해야 하면 그 조건을 검증하는 검사가 작성되지
   않는다.
3. 학생이 버튼을 사용할 수 없는 이유를 알 수 없다. 비활성 버튼은 이유가 제시되지 않으면
   오류로 인식된다.

그래서 규칙은 다음과 같다.

> 잠기는 요소에는 gate 함수가 하나 있고, boolean이 아니라 사유 목록을 반환한다.

사유는 코드이지 문장이 아니다. `{ code, params }` 형태로 반환하고 화면이 번역한다.
그리고 우선순위가 있다. 데이터가 없는 상태에서 "알고리즘을 선택하세요"를 표시하지 않는다.

## 구현하지 않은 것

한 가지는 보류했다. `trainGate` 함수를 실제로는 구현하지 않았다.

확인해 보니 `[학습하기]` 버튼이 참조하는 조건은 하나였다. 추가한 모델이 0개인지 여부다.
나머지는 이미 다른 위치에 분산되어 있었고 그 위치가 적절했다. 데이터, 타깃, 특성이 없으면
단계가 잠겨 해당 화면에 진입할 수 없고, 선택한 모델이 현재 조합에서 지원되지 않으면
학습은 수행되고 모델별로 사유가 기록된다. 실험 전체가 실패하는 경우는 없다.

구현이 하나뿐인 계약을 미리 설계하지 않는다. 두 번째 조건이 발생하는 시점에 gate를
구현하고, 그 시점은 검사가 알려 준다. 등록부와 동일한 원리다. 존재하지 않는 요구를 위해
추상을 미리 도입하면 그 추상은 추측으로 채워진다.

## 결과

군집(K-평균)과 이미지가 이 장치를 처음 사용했다. 두 경우 모두 등록부에 항목을 추가하는
작업으로 종료되었고, 화면 누락으로 인한 결함은 발생하지 않았다.

이 규칙들은 사람이 준수할 것으로 기대하지 않는다. `frontend/tests/ui-rules.spec.ts`가
소스를 검사해 강제한다. 사람에게 위임하지 않는 이유는
[규칙은 검사가 강제한다](../rules-and-their-limits/)에 정리했다.
