## 엑셀이 감당하지 못하는 지점

경기도교육청은 대입 상담용으로 『2027 수시NAVI』라는 엑셀 파일을 배포한다. 전국 대학의 입시 결과, 지원 경향, 환산 규칙이 시트 단위로 정리되어 있고, 진학 담당 교사가 여기에 우리 학교 학생의 성적을 입력해서 상담에 사용한다.

자료 자체는 훌륭하다. 문제는 전달 방식이다.

한 파일 안에 대학 데이터와 학생 데이터가 함께 존재한다. 그래서 담임에게 배포하려면 전교생 성적이 들어간 파일을 그대로 전달하게 된다. 반대로 교육청이 대학 데이터를 갱신하면 이미 입력한 학생 성적을 새 파일로 다시 옮겨야 한다. 두 종류의 데이터가 갱신 주기도 다르고 취급 기준도 다른데 한 파일에 결합되어 있다.

시트 조작도 부담이다. 논술 시트는 머리글이 복잡해서 열이 화면을 넘어가고, 필요한 열만 확인하려면 숨기기와 필터를 반복해야 한다. 상담 중에 할 작업이 아니다.

## 두 덩어리를 분리한다

설계의 출발점을 여기에 두었다.

| | 내용 | 갱신 주체 | 저장 위치 |
|---|---|---|---|
| 대학 데이터 | 전국 입시 결과, 지원 경향, 환산 규칙 | 유지보수자 (빌드 시점) | 실행 파일 내부에 봉인 |
| 학생 데이터 | 우리 학교 학생의 내신과 모의고사 | 진학 담당 교사 (앱에서) | 암호화된 `.navi` 파일 |

담임에게는 실행 파일과 `.navi` 파일 둘만 전달하면 된다. 대학 데이터는 실행 파일에 포함되어 있으므로 별도로 배포할 필요가 없고, 교육청이 자료를 갱신하면 실행 파일만 교체한다. 학생 데이터는 `.navi` 파일에만 존재하므로 대학 데이터 갱신이 학생 데이터를 건드리지 않는다.

이 구조는 School Record Editor에서 확립한 원칙과 같은 계열이다. 학생 개인정보는 교사의 기기를 벗어나지 않고, 도구의 갱신과 데이터의 수명이 분리되어야 한다.

## 기술 선택

Tauri와 Rust, Vue를 사용한다. 이 조합은 [학교생활기록부 에디터](../../school-record-app/school-record-editor-overview/)와 [학교장추천자 선발 관리 시스템](../../principal-candidate-manager/pcm-overview/)에서 이미 검증한 구성이다.

설치 절차 없이 실행 파일 하나로 동작해야 한다는 조건이 가장 크게 작용했다. 학교 PC의 보안 정책은 학교마다 다르고, 배포 대상은 내가 통제하지 않는 환경이다. 이 제약을 어떻게 확인했는지는 [PyInstaller에서 Tauri로](../../teacher-utility-kit/pyinstaller-to-tauri/)에 기록했다.

## 나흘

2026년 9월 12일 오전 10시 12분에 첫 커밋을 기록했고, 나흘 동안 작업이 이어졌다.

| 일자 | 국면 |
|---|---|
| 09-12 | 조회 화면 이전, 화면 정의를 데이터로 분리, 검사 체계 확립 |
| 09-13 | 암호화 용기 재설계와 외부 감사, 환산 규칙 문법 교체 |
| 09-14 | 검사가 통과시키던 구간 차단 |
| 09-15 | 릴리스 서명 체계와 갱신 경로 |

첫날 하루에만 마흔 건이 넘는 커밋이 기록됐다. 조회 전용 시트를 순서대로 이전하는 작업이 대부분이었으나, 그 과정에서 이후 전체 구조를 결정한 판단이 몇 가지 나왔다.

가장 중요한 것은 오후 12시 42분의 `화면 정의를 코드에서 데이터로 — screens.json`이다. 시트가 열 개를 넘어가면서 화면마다 컴포넌트를 작성하는 방식이 유지되지 않는다는 점이 드러났고, 화면의 구성을 데이터로 기술하고 렌더러 하나가 처리하는 구조로 전환했다. 이 판단의 경과는 다음 글에서 다룬다.

## 작업 규칙을 먼저 기록했다

구현보다 규칙을 먼저 확정한 항목이 둘 있다.

첫째, 문서에 세어서 나온 숫자를 기재하지 않는다. 오후 1시 15분에 `CLAUDE.md`로 확정했다.

> 테스트가 늘거나 열이 하나 생기는 순간 곧바로 틀린 문서가 되고, 아무도 고치지 않는다. 틀린 문서는 없는 문서보다 나쁘다.

세어야 확인되는 값은 검사 스크립트가 실행 시점에 계수해서 출력하도록 했다. 문서에는 규칙만 기재한다.

둘째, 화면에 표시되는 글은 한자어 동사로 작성한다.

> 제목·설명·안내 문구에 `견주다`·`갈리다`·`찾다` 같은 순수 한국어 동사를 쓰지 않는다. `비교하다`·`구분하다`·`확인하다` 로 쓴다. 선생님께 보이는 글이라 문어체가 자연스럽고, 같은 화면 안에서 말투가 갈리지 않는다.

적용 범위를 화면으로 한정하고 코드 주석과 작업 규칙 문서는 제외했다. 읽는 사람이 다르기 때문이다.

## 현재 상태

이 글을 작성하는 시점에도 작업이 진행 중이다. 릴리스 서명 체계를 구성하는 국면이고, 배포는 아직 하지 않았다.

시리즈의 나머지 글은 화면을 데이터로 기술한 구조, 조용한 오류를 빌드 실패로 전환한 방식, 그리고 배포한 뒤에는 변경할 수 없는 값을 검사가 보호하게 만든 과정을 다룬다.
