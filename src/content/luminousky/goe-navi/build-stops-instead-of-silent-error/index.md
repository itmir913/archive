## 경고는 사람이 확인하지 않는다

작업 규칙 문서의 두 번째 항목에 이렇게 기재했다.

> 자료가 어긋났을 때 **아무 말 없이 그럴듯한 값이 나오는 길을 남기지 않는다.** 경고는 사람이 안 본다. 빌드를 세운다.

이 도구는 대학 입시 자료를 계산해서 교사에게 제시한다. 환산 규칙이 잘못 적용되면 화면에는 정상적인 숫자가 표시되고, 그 숫자를 근거로 학생의 지원 대학이 결정된다. 계산이 중단되면 문제를 인지하지만, 계산이 완료되면 인지하지 못한다.

같은 구조의 실패를 이전에 여러 번 확인했다. [WordFinderApp이 20개월 동안 차단당하고 있었던 것](../../teacher-utility-kit/pyinstaller-to-tauri/)도, [ML Playgrounds에서 정규식 검사가 아무것도 검출하지 않는 상태로 통과하던 것](../../ml-playgrounds/audit-and-discipline/)도 전부 오류를 발생시키지 않았다.

## 조용히 틀리는 경로를 빌드에서 차단했다

첫날 오후 2시 20분의 커밋이다.

> `시트 번호에 뜻을 주고, 조용히 틀리는 길을 전부 빌드에서 막음`

시트 번호가 단순한 정수일 때는 잘못된 번호를 참조해도 다른 시트가 조회될 뿐이다. 번호에 의미를 부여하고 빌드 시점에 검증하면 존재하지 않는 참조가 빌드를 정지시킨다.

환산 규칙에도 같은 조치를 적용했다. 오후 1시 27분이다.

> `환산룰 검증을 줄 번호 대신 이름으로 짝짓고, 짝이 어긋나면 빌드가 잡게 함`

줄 번호로 대응시키면 원본 자료에 행이 하나 삽입되는 순간 전체 대응이 밀린다. 그리고 밀린 상태에서도 계산은 정상적으로 수행되어 틀린 결과를 산출한다. 이름으로 대응시키고 대응 실패를 빌드 실패로 전환했다.

밤 11시 10분에도 같은 종류의 작업이 이어졌다.

> `조용히 어긋나던 네 자리에 검사를 건다`

## 빈 값을 채우지 않는다

오후 4시 35분의 판단이다.

> `빈 성적을 메우지 않고, 영어 환산표가 성한지 읽을 때 본다`

학생 성적에 빈 칸이 있을 때 기본값으로 채우면 계산이 진행된다. 진행되면 안 된다. 미응시와 0점은 수학적으로 다른 값이고, 이 둘을 혼동하면 평균이 왜곡된다. score-reporter에서 [같은 결함을 수정한 기록](../../teacher-utility-kit/splitting-tools-into-repos/)이 있다.

영어 환산표는 읽는 시점에 무결성을 확인한다. 사용하는 시점이 아니라 읽는 시점인 이유는, 사용 시점에는 이미 다른 계산이 진행된 뒤여서 어디까지가 유효한 결과인지 판별하기 어렵기 때문이다.

## 문서에 계수한 숫자를 기재하지 않는다

오후 1시 15분에 별도의 규칙을 확정했다.

> README, `00 읽어보기` 시트, 코드 주석 어디에도 **세어서 나온 숫자**를 적지 않는다. 테스트가 늘거나 열이 하나 생기는 순간 곧바로 틀린 문서가 되고, 아무도 고치지 않는다. 틀린 문서는 없는 문서보다 나쁘다.

규칙 문서에 대조 예시를 함께 기재했다.

```
✗  npm run test 가 635건을 모두 통과하는지 확인하세요
✓  npm run test 가 모두 통과하는지 확인하세요

✗  논술 시트가 46열에서 29열로 줄어듭니다
✓  머리글이 복잡한 시트는 열이 절반 가까이 줄어듭니다
```

이 규칙이 앞의 항목과 같은 계열에 속한다. 틀린 문서도 조용히 실패하는 대상이다. 숫자가 어긋나도 아무 일이 발생하지 않고, 읽는 사람은 그 숫자를 신뢰한다.

계수해야 확인되는 값은 검사 스크립트가 실행 시점에 계수해서 출력한다. `✓ 오류 코드 24개 일치` 같은 형태다. 이러면 숫자가 항상 현재 상태를 반영하고, 어긋나면 검사가 실패한다.

예외는 변경되지 않는 값뿐이다. 안내 시트 앞의 두 자리 번호나 문법 예시에 포함된 `LARGE(2, korPct, matPct)` 같은 항목이 해당한다.

## 측정하고 기재한다

같은 날 저녁에 이 원칙이 다른 형태로 적용됐다.

```
19:51  열 너비를 적지 않고 잰다
20:04  열 너비를 머리글이 아니라 내용까지 보고 잡는다
```

열 너비를 상수로 기재하면 내용이 변경될 때 어긋난다. 측정해서 산출하면 항상 내용과 일치한다. ML Playgrounds에서 [기기 계층 표를 폐기하고 실측으로 전환한 판단](../../ml-playgrounds/limits-and-losses/)과 같은 구조다.

## 비용

이 방식에는 대가가 따른다. 빌드가 자주 정지한다. 자료를 한 줄 수정했을 뿐인데 검사 넷이 실패하는 상황이 발생하고, 그중 셋은 실제 문제가 아니라 검사가 과하게 엄격한 경우다.

첫날 저녁에 CI 실행 시간이 5분까지 증가했고, 오후 8시 59분에 55초로 단축했다.

> `ci 를 5분에서 55초로 줄이고, 찾아낸 과정을 docs 에 남긴다`

단축 과정을 `docs/build-speed.md`에 기록한 이유가 있다. 실행 시간이 다시 증가했을 때 어떤 항목을 확인해야 하는지가 그 문서에 있고, 없으면 같은 탐색을 반복하게 된다.

검사가 과하게 엄격한 문제 자체는 해결하지 않았다. 빌드가 정지하는 비용과 조용히 틀린 값이 교사에게 제시되는 비용을 비교하면 전자가 작다고 판단했다.
